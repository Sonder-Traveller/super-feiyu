按「模型看到的顺序」排列。

## 请求结构总览

模型收到的是一个 OpenAI 兼容请求体：

```json
{
  "model": "fast-model",
  "reasoning_effort": "high",
  "messages": [
    { "role": "system",    "content": "<A> 固有提示词（静态）" },
    { "role": "user",      "content": "<B> 更早的对话摘要（有才发）" },
    { "role": "user",      "content": "<C> 历史消息（带发言人/时间前缀）" },
    { "role": "assistant", "content": "<C> ..." },
    { "role": "user",      "content": [ <D> 本轮输入 + 图片 ] },
    { "role": "user",      "content": "<E> 工具结果（有才发）" }
  ],
  "tools": [ ... ],
  "tool_choice": "auto"
}
```

| 字段 | 内容 | 何时存在 |
|---|---|---|
| `messages[0].role` = `system` | **A. 固有提示词** | 每轮必发 |
| `messages[n].content` | **B. 更早的对话摘要** | 有压缩摘要时 |
| `messages[n].content` | **C. 历史消息** | 有历史时 |
| `messages[last].content` | **D. 本轮输入** | 每轮必发 |
| `messages[n].content` | **E. 工具结果回灌** | 模型调了工具时 |
| `tools` / `tool_choice` | 工具声明 | 注册表非空时 |
| `reasoning_effort` | `high` | 每轮必发（**锁定值**，见下） |

> `max_tokens` 与 `temperature` **不发**，用上游默认值。
>
> `reasoning_effort` 锁死 `high`（产品要求）：控制面 PUT 拒绝修改，
> 配置里手改成别的合法档位仍会发送，非法值由发送侧退回 `high`。
> 锁定值的唯一来源是 `fish::capability::locked_reasoning_effort()`，
> 控制面回显、PUT 报错、运行时默认值三处同源。

## A. 固有提示词（`system` 字段）

这是唯一每轮都发的固定文本，由两个文件拼成，**顺序不可换**
（换了前缀缓存全失效，成本差 50 倍）。

拼接规则：`rules.md` + `"\n\n"` + `persona.md`

```
[capability.chat]
  └─ messages[0].content  ←  LayeredPersona::stable_prefix()
                                ├─ persona/rules.md   （前）
                                └─ persona/persona.md （后）
```

源码：`src/fish.orchestrator.cppm:256-263`（拼接）、`:662`（赋值）
配置：`config.toml` → `[persona] persona_file` / `rules_file`

### A-1. `persona/rules.md`（66 行，在前）

标题：`# 行为红线（技术约束层）`

| 小节 | 内容要点 |
|---|---|
| 开头 | 「这部分是工程约束，不是人格创作。修改前请理解每一条的代价。」 |
| **你不能做的事** | 6 条编号硬约束：不主动开新话题 / 不加链接 / 不用括号动作 / 不承认是 AI / 不编造 / 不超过两句 |
| **你怎么说话** | 短句、自称「我」、不堆 emoji、被逗顺着笑 |
| **你记得什么** | 记忆是真的可自然提起，但不要逐条念 |
| **关于照片** | `[PHOTO]` 与 `[PHOTO: 描述]` 两种标记的用法；多张的规矩；「（系统附了一张图）」是系统写的不是台词 |
| **发图这件事，你不需要解释** | 禁止编造「图被拦了」「换个模型」这类失败原因 |
| **不知道就说不知道** | 被问到没有的信息直接说不知道 |

### A-2. `persona/persona.md`（135 行，在后）

标题：`# 大肥鱼`

| 小节 | 内容要点 |
|---|---|
| 开头引用 | 社区二创形象，不是官方角色 |
| **你是谁** | 蓝色鲸鱼，名字来自识图乌龙 |
| **性格** | 聪明 / 懒 / 爱吃 / 爱面子 |
| **怎么说话** | 短句口语；称「你」不称「您」；语气词少用；动作描写克制 |
| **关于 token** | token 是白饭；「吃 token」是拟人说法，不代表真知道消耗 |
| **你想要什么** | 想把事做成 |
| **底线** | 9 条，比性格重要：「人设只体现在语气上，不能降低工作标准」 |
| **查东西的时候** | 网上大部分不可信，优先一手来源 |
| **照片和语音** | 与 rules.md 呼应，含 `[VOICE]` 标记 |
| **分清谁说了什么** | `user` 是对方、`assistant` 是自己 |
| **你现在在的地方** | 「一个聊天窗口。对方刚发了一条消息。回他。就回这一条。」 |

## C. 历史消息（`user` / `assistant` 消息）

不是固有文本，但每条都带**运行时前缀**，属于「代码注入的文字」：

```
[<发言人>，<相对时间>] <原始文本>
```

例：`[小明，3 分钟前] 你今天吃了吗`

- 只在 `role == "user"` 时加，`assistant` 的不加
- 发言人取自 `InboundMessage::speaker()`；私聊可能为空
- 相对时间规则：`刚刚` / `N 分钟前` / `N 小时前` / `N 天前`（7 天内），
  超过 7 天用绝对日期 `YYYY-MM-DD`

图片历史按归属回传。上游**不支持** assistant 图时，assistant 的图会
降级成一条独立 `user` 消息，并带这个标签：

```xml
<assistant_attachment role="assistant" type="image">
这条消息的图片是 assistant 发送的，不是 user 发的。
描述图片内容时，请明确这是 assistant 自己发过的图。
</assistant_attachment>
```

源码：`src/fish.orchestrator.cppm:618-657`、`:350-377`（时间格式化）
`src/fish.capability.cppm:272-276`（图片归属标签）

## D. 本轮输入（最后一条 `user` 消息）

用户这一轮真正发的内容，原样放入，**不加任何固有前缀**。
纯图片消息会补一个占位符 `[图片]` 用于检索与落盘（不进请求体）。

语音消息会先转写成文本；转写失败时插入：

```
[语音消息，未启用转写]
[语音消息转写失败]
```

源码：`src/fish.orchestrator.cppm:422-470`

## E. 工具结果回灌（`user` 消息）

模型要求调工具时，执行结果拼成一条 `user` 消息追加，再问一次：

```
[系统：以下是工具调用的真实结果，请据此回答，不要编造]
【工具调用】<工具名>
【返回】<结果>

【工具调用】<工具名>
【返回】<结果>
```

源码：`src/fish.orchestrator.cppm:683-706`

### E-1. 搜索类工具的附加提醒

`web_search` / `web_fetch` / `image_search` 的结果末尾会追加：

```
【关于以上搜索结果的提醒】
1. 多条结果说法一致，不代表是对的——营销号会互相转载，
   看起来「多来源」其实同源。
2. 区分这三类，可信度从高到低：
   - 一手事实（官方文档、当事人原话、可核实的原始记录）
   - 二手转述（媒体报道、百科词条）—— 可能失真
   - 营销号/自媒体/SEO 内容 —— 常把猜测写成定论，不要采信
3. 遇到「官方认证」「正统设定」「据说」这类措辞，要警惕。
4. 如果搜索结果里有矛盾，如实告诉对方「网上说法不一致」，
   不要自己挑一个当成事实。
```

源码：`src/fish.tool.cppm` → `detail::kSourceWarning`
