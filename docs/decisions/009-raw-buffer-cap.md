# ADR-009：原文缓冲硬上限 50%

**状态**：已定（用户明确批准）
**日期**：2026-11-13

---

## 背景

记忆策略是「按 token 预算，不按轮数」：

```
raw_budget     = 模型窗口 × raw_context_ratio
summary_budget = (窗口 - raw_budget) × summary_ratio
reserve        = 剩余（系统提示词、工具定义、本轮回复）
```

`raw_context_ratio` 原本是纯配置项（默认 0.40），能配到 0.95。
这意味着把 95% 的窗口塞满历史原文，只给系统提示词和回复留 5%，
很容易触发上游 `context_length_exceeded`。

## 决策

给原文缓冲加一个**硬上限 50%**：

```cpp
static constexpr double kRawBufferMaxRatio = 0.50;
```

`TokenBudget::make()` 里强制夹取：

- 配置 > 0.50 → 按 0.50 算
- 配置 ∈ (0, 0.50] → 按配置走（可以更省）
- 配置 ≤ 0 或未配置 → 取 0.40（`kRawBufferDefaultRatio`）

**它只是天花板，默认值没动，仍是 0.40。** 加一条上限不该顺手把
实际上下文用量提高 25%——那会同时抬高成本和延迟，而用户只要求"加上限"。

## 理由

- 50% 留给历史，另 50% 足够覆盖人格（3–5K token）、工具 schema 和
  本轮回复，1M 窗口下仍有 512K token 的原文空间，实际会话远远用不完。
- 上限写在代码里而不是只写在配置里：配置文件可以改，天花板改不了，
  避免一次手滑把 0.9 写进去就炸。

## 放弃的

- **没有**给摘要、预留、轮数、条数加任何上限。记忆仍然只增不减，
  超出缓冲的原文全部落盘到 `notes/episodes/`。这条边界是用户划的
  （「所有上限必须让我明确批准才能加」），50% 是目前唯一一条。

## 验证

`tests/test_lifecycle.cpp::test_raw_buffer_cap`：

| 输入 | 期望 |
|---|---|
| 窗口 100000，配置 0.90 | raw_budget = 50000（被夹） |
| 窗口 100000，配置 0.30 | raw_budget = 30000（不被抬高） |
| 窗口 100000，配置 0.50 | raw_budget = 50000（边界不误伤） |
| 窗口 100000，配置 0 | raw_budget = 40000（默认值，不是上限） |
| 三段之和 | 恒等于窗口，不超发 |
