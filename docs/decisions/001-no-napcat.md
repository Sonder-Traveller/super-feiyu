# ADR-001：不用 NapCat，直连官方 Bot API

**状态**：已定
**日期**：2026-11-12

---

## 背景

社区主流方案是 **AstrBot + NapCat**。NapCat 通过套壳 NTQQ 桌面客户端
实现 OneBot 协议，能模拟真实 QQ 号，功能完整（群聊、私聊、全媒体）。

## 问题

NapCat 必须跑完整的 NTQQ 客户端进程树（bash → Xvfb → QQ → ...），
实测内存占用：

| 组件 | 空闲内存 | 进程数 |
|---|---|---|
| NapCat | **532 MiB** | 86 |
| AstrBot | 323 MiB | 7 |
| 合计 | **≈ 855 MiB** | 93 |

目标机器是 **2C1G**。系统本身占 100–150 MB，剩不到 900 MB。
**这条方案在目标机器上必 OOM，没有优化空间。**

## 决策

**直连 QQ 官方机器人开放平台 API**（WebSocket 网关），不使用任何协议端。

## 代价（必须接受）

| 放弃的能力 | 影响 |
|---|---|
| 主动消息 | 官方 2025-04-21 起停用，无解 |
| 无限制回复 | 被动回复：单聊 60min/4 条，群聊 5min/5 条 |
| 真实 QQ 号身份 | 只能以 "bot" 身份存在，需要用户 @ |
| 任意群自由加入 | 需沙箱配置 + 群名带"测试"，上线需审核 |
| 外部链接 | 可能被拦截 |

## 收益

| 收益 | 说明 |
|---|---|
| 内存 | 省掉 532 MB，这是决定性因素 |
| 合规 | 官方协议，**零封号风险** |
| 部署 | 无 Docker、无 Xvfb、无 Python |
| 稳定性 | 无客户端崩溃问题 |

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| Lagrange.OneBot | C# + .NET 运行时，体积大；维护状态不确定 |
| 微信 ClawBot（个人号） | 仅单聊、仅文本、24h 需重扫码，不适合主力 |
| go-cqhttp | 已停止维护 |

## 后果

- `ChannelCapability` 必须声明 `max_replies_per_message`
- `ReplyBudget` 成为必需组件，不是优化项
- 微信通道降级为可选补充（单聊场景）
