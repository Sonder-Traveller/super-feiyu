# ADR-006：会话串行化用条带锁，不用每会话队列

**状态**：已定

---

## 决策

按 `conversation_id` 哈希到 **64 个互斥锁**（条带锁）：

```cpp
std::array<std::mutex, 64> shards_;
auto& lock_for(conv_id) {
  return shards_[std::hash<std::string>{}(conv_id) % 64];
}
```

## 问题

两个 worker 同时处理同群两条消息会导致：

1. 回复顺序颠倒（后发的先回）
2. 记忆写入竞争（上下文错乱）
3. 上下文不一致（第二条看到的记忆缺第一条）

## 被否决的方案

### 每会话一个队列

| 问题 | 说明 |
|---|---|
| 内存不可控 | 会话数可达上千，每个 mutex + deque 约 200 字节 → 200 KB 起，且只增不减 |
| 生命周期管理 | 会话长期不活跃时需要回收，逻辑复杂 |
| 仍需调度器 | 要么每会话一线程（更糟），要么单线程轮询（延迟高） |

### 全局单锁

| 问题 | 说明 |
|---|---|
| 完全串行 | 两个不相关群的消息互相阻塞 |
| 慢请求拖累全局 | 一个 8 s 的 LLM 调用卡住所有消息 |

### 无锁 + 顺序重排

过度设计。当前规模下不值得。

## 条带锁的优势

| 项 | 值 |
|---|---|
| 固定内存 | 64 × sizeof(mutex) ≈ 2.5 KB |
| 无生命周期问题 | 数组常驻 |
| 实现简单 | 一个 `lock_guard` |
| 足够正确 | 同会话必串行 |

## 碰撞代价

两个不相关会话哈希到同一槽时短暂串行。

- 百级会话 + 64 槽：碰撞概率约 70%（生日悖论）
- 但碰撞**只增加延迟**（排队），**不影响正确性**
- 平均等待时间 = 另一会话的处理时长，通常 < 3 s

**权衡**：用可接受的延迟换固定内存和实现简单性，值得。

## 参数选择

64 是折中：

| 槽数 | 内存 | 碰撞 |
|---|---|---|
| 16 | 0.6 KB | 高 |
| **64** | 2.5 KB | 中 |
| 256 | 10 KB | 低 |

若实测碰撞严重（日志里锁等待时间偏高），可调到 256，代价仅 10 KB。
