# 记忆系统设计

> 类比人脑结构：**短时记忆（上下文/内存）与长时记忆（持久化/外存）分离**，
> 中间有巩固（consolidation）与遗忘（forgetting）两个方向的过程。

这是本项目的核心模块。其余模块都是为它服务的管道。

---

## 1. 为什么不能只做一个"消息表"

大多数机器人框架的记忆就是一个 `messages` 表 + 最近 N 条塞进上下文。
这种做法在长期使用下必然崩坏：

| 问题 | 后果 |
|---|---|
| 上下文只装得下最近几十条 | 三个月前说的事完全失效 |
| 全部历史塞进去 | token 爆炸，且大部分无关 |
| 没有重要性区分 | "嗯""好的"和"我妈妈住院了"权重相同 |
| 只增不减 | 数据库与召回噪声同步膨胀 |
| 不分时间 | 昨天说的和去年的混在一起 |

**核心判断**：记忆不是"存过的东西"，而是"被巩固下来的东西"。
存和记是两件事。

## 2. 三层结构

```
┌─────────────────────────────────────────────────────────────┐
│ L1 感觉记忆（Sensory）  —— 不落地，纯内存                     │
│    当前这条消息，处理完即弃                                    │
│    生命周期：一次请求                                          │
│    容量：1                                                    │
├─────────────────────────────────────────────────────────────┤
│ L2 短时记忆（Working）  —— 内存环形缓冲                       │
│    最近 N 轮对话原文，参与每轮上下文                           │
│    生命周期：进程内，重启即失（可从 L3 重建）                   │
│    容量：每会话 20 轮（可配）                                  │
│    类比：内存 / 工作记忆                                       │
├─────────────────────────────────────────────────────────────┤
│ L3 长时记忆（Long-term）—— 持久化旁路文件 + SQLite            │
│    ┌───────────────────────────────────────────┐            │
│    │ 3a 情景记忆（Episodic）  原始对话流水        │            │
│    │     "10月3日她和我说了加班到很晚"            │            │
│    ├───────────────────────────────────────────┤            │
│    │ 3b 语义记忆（Semantic）  提炼出的事实        │            │
│    │     "她在一家做芯片的公司上班"               │            │
│    ├───────────────────────────────────────────┤            │
│    │ 3c 程序记忆（Procedural）行为模式与偏好      │            │
│    │     "她不喜欢被追问细节，喜欢短回复"          │            │
│    └───────────────────────────────────────────┘            │
│    生命周期：永久，带衰减                                     │
│    容量：受配额约束，LRU + 重要性双重淘汰                      │
│    类比：外存 / 长期记忆                                       │
└─────────────────────────────────────────────────────────────┘
              ▲ 巩固（consolidate）        │ 遗忘（forget）
              └────────────────────────────┘
```

### 2.1 三层的职责边界

| 层 | 存什么 | 谁读 | 是否持久化 | 检索方式 |
|---|---|---|---|---|
| L1 | 当前消息 | orchestrator | ❌ | 直接使用 |
| L2 | 最近 20 轮原文 | orchestrator（每轮） | ❌ 内存 | 全量注入 |
| L3a | 历史对话 | 巩固器、召回 | ✅ SQLite | 向量 + 时间 |
| L3b | 提炼事实 | 召回 | ✅ SQLite | 向量 |
| L3c | 行为模式 | 人格拼装 | ✅ 旁路文件 | 全量注入（量小） |

**关键**：L2 与 L3 是**两种不同的记忆**，不是同一份数据的两种视图。
L2 是"刚才在聊什么"，L3 是"关于这个人我知道什么"。

## 3. 巩固：从 L2 到 L3

### 3.1 触发时机

| 触发 | 条件 | 说明 |
|---|---|---|
| 轮数触发 | 每 20 轮 | 主要路径 |
| 时间触发 | 会话空闲 30 分钟 | 收尾时巩固一次 |
| 进程退出 | 优雅退出 | 防止丢失 |

**不在每轮巩固**：一次 LLM 提炼成本约 2000 token，
每轮都做会让成本翻倍。20 轮是成本与时效的平衡点。

### 3.2 巩固流程

```
L2 的 20 轮原文
      │
      ▼
┌─────────────────┐
│ 提炼 LLM 调用    │  system: 固定的巩固指令
│ （另一次请求）    │  user: 20 轮对话
└────────┬────────┘
         │ 结构化输出（JSON）
         ▼
┌─────────────────────────────────────────┐
│ {                                        │
│   "episodes": [                          │  → L3a 情景
│     {"summary": "...", "importance": 0.7}│
│   ],                                     │
│   "facts": [                             │  → L3b 语义
│     {"subject": "用户", "content": "...",│
│      "confidence": 0.9}                  │
│   ],                                     │
│   "traits": [                            │  → L3c 程序
│     {"pattern": "...", "evidence": 3}    │
│   ]                                      │
│ }                                        │
└─────────────────────────────────────────┘
         │
         ▼
   写入 SQLite + 生成向量
         │
         ▼
   L2 清空（或保留滑动窗口）
```

### 3.3 巩固的独立性（重要设计约束）

> **巩固是一次独立的 LLM 调用，使用独立的 system prompt，
> 且不与对话共享前缀缓存。**

理由：
- 巩固 prompt 与对话 prompt 完全不同，共享缓存反而污染
- 巩固是离线任务，延迟不敏感
- 失败不影响对话（降级：跳过本轮巩固，下轮重试）

**成本**：每 20 轮一次，约 2000 token。按 100 轮/天算，每天 5 次，
约 1 万 token/天 —— **比对话本身便宜得多**。

### 3.4 巩固的幂等性

同一批 L2 可能因崩溃被重复巩固。用 `batch_id`（会话 id + 轮次范围哈希）去重：

```sql
CREATE UNIQUE INDEX idx_batch ON episodes(batch_id);
```

重复写入时 `INSERT OR IGNORE`。

## 4. 上下文管理：预算内全量，超出则压缩存盘

### 4.1 为什么需要窗口

模型上下文有限，不能把所有历史都塞进去。但**也不能随便丢**。

| 做法 | 问题 |
|---|---|
| 固定保留最近 N 轮 | N 是拍脑袋定的，与模型能力无关 |
| 全量塞进去 | 超出窗口直接报错 |
| 超出的删掉 | 记忆丢失，用户白聊了 |

本项目的做法：**按模型窗口的百分比留原文，超出的压缩成摘要，原文全部存盘。**

### 4.2 上下文按「百分比预算」，不按固定轮数

**没有固定轮数上限。** 给模型多少原文，由模型的上下文窗口决定：

```
预算 = 模型窗口 × 比例
```

| 参数 | 默认 | 含义 |
|---|---|---|
| `model_context_tokens` | 131072 | 模型窗口大小 |
| `raw_context_ratio` | **0.40** | 原文可占 40% |
| `summary_ratio` | 0.25 | 余下部分里，摘要占 25% |

为什么不是 100%：还要给系统提示词（人格）、工具定义、本轮回复留位置。

**预算内一条不省。** 从最新往回数，能放下多少条就给多少条，
不是「固定 20 轮」这种一刀切。

### 4.3 超预算时：压缩，不丢弃

```
原始对话 token > raw_budget
        ↓
最早的 N 条 → 摘要（模型生成，滚动累加）
        ↓
这 N 条原文 → 落盘到 notes/episodes/ + 建向量索引
        ↓
短时记忆只留预算内的部分
```

**关键：原文不丢。** 它被写成情景记忆存进旁路文件，
同时进 SQLite 索引，之后模型可以用检索工具找回。

### 4.4 存储不设上限

去掉了 `max_facts` / `max_episodes` 这类条数配额。

| 项 | 行为 |
|---|---|
| 事实记忆 | 全部保留，不淘汰 |
| 情景记忆 | 全部保留，不淘汰 |
| 磁盘增长 | 由用户自行清理 `data/memory/notes/` |

理由：记忆是有价值的资产，不该由程序擅自删除。
真需要清理时，用户可以手改 Markdown 文件（它可读、可 diff）。

### 4.5 冲突处理

同一 subject 有矛盾事实时（"讨厌咖啡" vs "开始喝咖啡"）：

**不删除旧的，标记 `superseded_by`**：

```sql
ALTER TABLE facts ADD COLUMN superseded_by INTEGER REFERENCES facts(id);
```

召回时只看 `superseded_by IS NULL` 的条目。
保留历史便于追溯（"你之前不是讨厌咖啡吗？"）。

## 5. 检索：混合而不是纯向量

### 5.1 为什么纯向量不够

| 场景 | 纯向量的问题 |
|---|---|
| "我上次说的那个游戏叫什么" | 需要精确名词匹配，向量反而模糊 |
| "昨天" | 需要时间过滤，向量无时间概念 |
| "你记得我喜欢什么吗" | 需要按 subject 聚合，不是相似度 |
| 长尾专有名词 | embedding 对罕见词表征差 |

### 5.2 三路召回

```
                   查询文本
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   ┌─────────┐  ┌──────────┐  ┌──────────┐
   │ 向量路   │  │ 关键词路  │  │ 时间路    │
   │ 余弦相似 │  │ FTS5/BM25│  │ 最近 N 天 │
   └────┬────┘  └────┬─────┘  └────┬─────┘
        │            │             │
        └────────────┼─────────────┘
                     ▼
              ┌─────────────┐
              │ RRF 融合     │  倒数排名融合
              └──────┬──────┘
                     ▼
              ┌─────────────┐
              │ 权重衰减过滤  │  weight > min
              └──────┬──────┘
                     ▼
              ┌─────────────┐
              │ top_k 注入   │
              └─────────────┘
```

### 5.3 RRF 融合

倒数排名融合（Reciprocal Rank Fusion），无需调权重：

```
score(doc) = Σ_over_paths  1 / (k + rank_in_path)
```

`k` 取 60（业界常用默认值）。

**为什么用 RRF 而不是加权分数**：
- 三路的分数尺度完全不同（余弦 vs BM25 vs 时间）
- 归一化会引入额外超参
- RRF 只看排名，对尺度不敏感，鲁棒

### 5.4 时间路的作用

"昨天""刚才""上周"这类查询，向量完全无效。
时间路直接按 `created_at DESC` 取，然后交给 RRF 与其他路融合。

**实现**：检测查询中的时间词，若命中则启用时间路：

```
昨天 / 今天 / 刚才 / 上周 / 上次 / 最近
```

### 5.5 检索预算

| 路 | 候选数 |
|---|---|
| 向量 | 20 |
| 关键词 | 20 |
| 时间 | 10 |
| **融合后注入** | **top 5** |

**注入 5 条**：多了挤占上下文，少了召回不足。
5 条约 300–500 token，可接受。

## 6. 存储：旁路文件 + SQLite 混合

### 6.1 为什么用旁路文件

用户明确要求"持久化旁路文件/外存"。

**旁路文件的价值**：

| 优点 | 说明 |
|---|---|
| 人可读 | Markdown，出问题能直接看 |
| Git 可管理 | 记忆可版本化、可 diff |
| 易迁移 | 拷走即用，不依赖 SQLite 版本 |
| 易修复 | 手改文件比改数据库安全 |
| 透明 | 用户能知道"她记住了什么" |

**SQLite 的价值**：向量检索、FTS5、事务、并发。

### 6.2 混合架构

```
data/
├── memory/
│   ├── index.db              # SQLite：索引 + 向量 + 元数据（二进制）
│   └── notes/                # 旁路文件（人可读）
│       ├── facts.md          # L3b 语义记忆
│       ├── episodes/
│       │   ├── 2026-11.md    # 按月的 L3a 情景摘要
│       │   └── 2026-10.md
│       └── traits.md         # L3c 程序记忆
```

**双写规则**：

| 数据 | SQLite | 旁路文件 | 谁是权威 |
|---|---|---|---|
| 向量 | ✅ | ❌ | SQLite |
| facts | ✅ 索引 | ✅ 正文 | **文件** |
| episodes | ✅ 索引 | ✅ 正文 | **文件** |
| traits | ✅ | ✅ | **文件** |

**关键决策：旁路文件是权威源，SQLite 是可重建的索引。**

理由：文件可读、可手改、可 git 管理。SQLite 若损坏，从文件重建即可。

### 6.3 重建流程

```
启动时：
  if (SQLite 缺失 或 校验和与文件不符) {
      扫描 notes/*.md
      解析结构化块
      重新生成向量
      重建 SQLite
  }
```

向量重算需要调 embedding API。1 万条约 40 分钟（10 RPM）。
**所以 SQLite 不能轻易删** —— 但至少数据不会永久丢失。

### 6.4 文件格式

`facts.md`：

```markdown
# 关于用户的长期记忆

<!-- 本文件由 super-feiyu 自动维护，可手工修正 -->

## 基本信息
- [id:f1] 在一家做芯片的公司上班 (置信度 0.9, 2026-10-03)
- [id:f2] 养了一只叫豆豆的猫 (置信度 0.95, 2026-10-05)

## 偏好
- [id:f3] 喜欢短回复，讨厌被追问细节 (置信度 0.8, 2026-10-10)
- [id:f4] ~~讨厌咖啡~~ → 被 f9 取代 (2026-10-20)

## 事件
- [id:f9] 开始喝咖啡了，因为加班 (置信度 0.85, 2026-11-01)
```

**解析规则**：单个 `- ` 开头，`[id:xxx]` 定位，括号内元数据。
人工可编辑，解析器容忍格式不严格。

## 7. 与上下文的接口

### 7.1 每轮注入什么

```
┌──────────────────────────────────────┐
│ system（稳定前缀）                     │  ← 缓存命中
├──────────────────────────────────────┤
│ L3c traits.md 全文                    │  ← 量小，全量注入
│   （行为偏好，约 100 token）           │
├──────────────────────────────────────┤
│ L2 短时记忆（最近 20 轮原文）           │  ← 追加式
├──────────────────────────────────────┤
│ L3b 召回的事实（top 5）                │  ← 动态
├──────────────────────────────────────┤
│ L3a 召回的情景（top 3）                │  ← 动态
├──────────────────────────────────────┤
│ 当前用户消息                           │
└──────────────────────────────────────┘
```

### 7.2 缓存影响

**关键问题**：L2 每轮变化，会破坏前缀缓存吗？

**不会。** 因为：
- system 在前，L2 在后
- L2 是**追加式**的：旧内容不变，只在末尾加新的
- 所以 `system + L2 前 N 轮` 仍命中缓存，只有新增部分未命中

**但 L3 召回是动态插入的**，位置在 L2 之后，所以：
- L3 之前的全部命中 ✅
- L3 及之后未命中 ❌

这就是为什么 L3 要放在**尽可能靠后**的位置，且**条数要少**。

### 7.3 L3 注入的 token 预算

| 项 | token |
|---|---|
| traits 全文 | ~100 |
| facts top 5 | ~200 |
| episodes top 3 | ~150 |
| **合计** | **~450** |

450 token 未命中的成本：450 × 1 元/百万 = **0.00045 元/轮**。
100 轮/天 = **0.045 元/天** ≈ 1.4 元/月。可接受。

## 8. 配置

```toml
[memory]
# L2 短时记忆
working_rounds = 20           # 内存中保留的轮数
consolidate_every = 20        # 每多少轮触发巩固
consolidate_idle_minutes = 30 # 空闲多久触发巩固

# L3 长时记忆（淘汰按容量，不按时间）
max_facts = 2000              # 事实条数上限，超过就按权重淘汰
max_episodes = 5000           # 情景条数上限
# 权重 = confidence × 0.5^(age_days / 30)，仅在超配额时用于排序

# 检索
recall_top_k = 5              # 注入的 facts 条数
episode_top_k = 3             # 注入的 episodes 条数
rrf_k = 60                    # RRF 参数
enable_time_path = true       # 是否启用时间路
enable_keyword_path = true    # 是否启用关键词路

# 存储
db_path = "data/memory/index.db"
notes_dir = "data/memory/notes"
rebuild_on_mismatch = true    # 索引与文件不符时重建
```

## 9. 模块划分

记忆系统单独成层，不塞进现有 `store`：

```
include/fish/memory/
  ├── working_memory.hpp      # L2：内存环形缓冲
  ├── long_term_memory.hpp    # L3：接口
  ├── consolidator.hpp        # L2 → L3
  ├── retriever.hpp           # 三路召回 + RRF
  ├── forgetting.hpp          # 衰减与淘汰
  ├── notes_store.hpp         # 旁路文件读写与解析
  └── index_store.hpp         # SQLite 索引与向量
```

### 9.1 与已有 `IMemoryStore` 的关系

现有 `IMemoryStore`（`append/recall/recent`）太粗糙，无法表达三层结构。

**决策**：保留 `IMemoryStore` 作为最底层接口，在其上建新层：

```
WorkingMemory    ──▶ 内存实现，不依赖 IMemoryStore
LongTermMemory   ──▶ 聚合 NotesStore + IndexStore
MemorySystem     ──▶ 统一门面，给 orchestrator 用
```

`orchestrator` 只依赖 `MemorySystem` 的门面：

```cpp
class MemorySystem {
  // 每轮调用：拿上下文
  struct Context {
    std::vector<Message> working;      // L2
    std::vector<Fact>    facts;        // L3b
    std::vector<Episode> episodes;     // L3a
    std::string          traits;       // L3c
  };
  Result<Context> gather(const InboundMessage& msg);

  // 每轮调用：记录
  Error record(const Message& user, const Message& assistant);

  // 后台调用：巩固
  Result<ConsolidateReport> consolidate(const std::string& conv_id);
};
```

## 10. 待定事项

| 事项 | 选项 | 倾向 |
|---|---|---|
| 巩固用哪个模型 | 同对话模型 / 更便宜的 | **同模型**（deepseek-flash 已够便宜） |
| 是否需要"记忆检索"指令 | 需要 / 不需要 | 不做（被动场景，用户不会查） |
| traits 如何更新 | 每次巩固重写 / 追加证据 | **证据计数**（≥3 次才确立） |
| 跨会话记忆 | 全局共享 / 每会话独立 | **全局共享**（同一用户的鱼只有一条） |
| 记忆导出 | 支持 / 不支持 | 支持（文件本身就是导出） |
| 向量重建限流 | 无 / 限流 | **限流 50ms/条**（避免 429） |

## 11. 测试要点

| 用例 | 断言 |
|---|---|
| L2 环形缓冲容量 | 超过 20 轮后最旧的被丢弃 |
| 巩固幂等 | 同一 batch 重复巩固不产生重复条目 |
| 巩固失败降级 | LLM 失败时不阻断对话，L2 不清空 |
| 权重衰减计算 | 30 天不用权重减半 |
| 常用记忆不衰减 | 召回后 last_used_at 刷新 |
| 冲突标记 | 新事实正确设置 superseded_by |
| 三路召回融合 | 构造三路都有命中的用例，验证 RRF 排序 |
