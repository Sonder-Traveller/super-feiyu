# super-feiyu · 架构设计

> 本文是全部模块设计的基准。各模块细节见 `docs/modules/`，关键取舍见 `docs/decisions/`。

---

## 1. 设计目标

| 目标 | 量化指标 | 说明 |
|---|---|---|
| 内存可控 | 常驻 **< 100 MB** | 不含 SQLite 页缓存与内核 buffer |
| 本机零推理 | 0 个模型权重 | 全部远程 API |
| 成本可控 | **< 50 元/月** | 核心靠前缀缓存命中率 |
| 冷启动快 | < 2 s | 无模型加载 |
| 崩溃可恢复 | 重启不掉记忆 | 状态全落盘 |
| 迁移成本低 | 拷 `data/` 即走 | 无环境依赖 |

### 非目标

以下明确**不做**，避免范围蔓延：

- ❌ 不做主动消息（平台已停用，且与「被动对话」冲突）
- ❌ 不做多机器人实例管理（一个进程一条鱼）
- ❌ 不做 Web 管理面板（配置走文件，观测走日志/指标）
- ❌ 不做插件市场（能力内置，扩展靠改代码）
- ❌ 不做本地模型兜底（内存不允许）

---

## 2. 为什么自己做

主流方案 **AstrBot + NapCat** 在 1C1G 上不可行，且职责边界模糊。

| 维度 | AstrBot + NapCat | super-feiyu |
|---|---|---|
| 内存 | NapCat 532 MB + AstrBot 323 MB ≈ **855 MB** | 目标 **< 100 MB** |
| 协议端 | 套壳 NTQQ 桌面客户端 | 直连官方 API，**无协议端** |
| 依赖 | Python + Docker + Xvfb | 单个静态二进制 |
| 职责边界 | 插件层混杂交错 | **编译期强制分层** |
| 成本控制 | 靠人自觉 | 前缀缓存由接口强制 |
| 故障定位 | 跨进程、跨语言 | 单进程、结构化日志 |

关键判断：**NapCat 是内存杀手，因为它必须跑完整 QQ 客户端。**
直连官方 Bot API 就绕过了这个根本矛盾。

## 3. 分层与依赖方向

```
┌──────────────────────────────────────────────────────────┐
│                      runtime 运行时                       │
│   配置加载 · 启动编排 · 日志 · 指标 · 优雅退出            │
└──────────────────────────┬───────────────────────────────┘
                           │ 组装
┌──────────────────────────▼───────────────────────────────┐
│                  orchestrator 编排层                      │
│   唯一持有业务决策：要不要回 · 回什么 · 怎么回            │
│   ReplyPolicy · ReplyBudget · Dedup · 会话串行化          │
└──────────────────────────┬───────────────────────────────┘
                           │ 只依赖接口
     ┌──────────┬──────────┼──────────┬──────────┐
     ▼          ▼          ▼          ▼          ▼
 transport  capability   store     persona    （接口由 core 定义）
 传输        远程能力     存储       人格
     │          │          │          │
     ▼          ▼          ▼          ▼
 QQ官方      DeepSeek    SQLite    persona.md
 微信iLink   硅基流动     + 向量     + rules.md
             Edge-TTS
```

### 3.1 依赖规则（编译期强制）

| 规则 | 强制手段 |
|---|---|
| 上层可依赖下层，反之禁止 | CMake target 级 `target_link_libraries` |
| `core` 不依赖任何实现 | `fish_core` 不链接 http/sqlite 库 |
| 实现层互相不可见 | 各自独立 target，接口注入 |
| 禁止头文件互相包含 | CI 用 `include-what-you-use` 检查 |

具体做法：`core` 是纯头文件 + 极少量实现，**不 include 任何第三方库头**。
`transport`、`capability`、`store` 各自编译为静态库，只在 `runtime` 里被同时链接。
**违反依赖方向的代码会链接失败，而不是靠 code review 抓。**

## 4. 数据流

### 4.1 一次完整交互

```
[平台] ──消息──▶ transport::poll()
                      │ InboundMessage
                      ▼
              ┌───────────────┐
              │ 去重 message_id│  重复直接丢弃
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ 时效检查       │  超过被动窗口 80% 直接丢弃
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ ReplyPolicy   │  群聊未 @ → 静默结束
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ 多模态归一化   │  语音→STT→文本；图片透传
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ 记忆召回       │  embedding → 向量检索
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ 提示词组装     │  静态 system + 历史 + 动态尾
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ ChatModel     │  DeepSeek
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ 落盘           │  用户+助手双写
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ ReplyBudget   │  逐条 consume，超限即停
              └───────┬───────┘
                      ▼
              ┌───────────────┐
              │ TTS（可选）    │  Edge-TTS
              └───────┬───────┘
                      ▼
              transport::send() ──▶ [平台]
```

### 4.2 关键路径上的失败语义

**任何一步失败都不能导致「不回复」，除非策略明确要求静默。**

| 失败点 | 行为 |
|---|---|
| 去重命中 | 静默丢弃，记 metric |
| 消息已过期 | 静默丢弃，记 metric |
| 策略判定不回 | 静默结束，记 metric |
| STT 失败 | 用占位文本继续，**不丢消息** |
| 记忆召回失败 | 无记忆上下文继续 |
| ChatModel 失败 | 重试 → 仍失败则回固定降级文案 |
| TTS 失败 | 只发文本 |
| 发送失败 | 按通道重试语义处理，不无限重试 |

## 5. 并发模型

### 5.1 线程划分（固定 5 + N）

| 线程 | 数量 | 职责 | 阻塞点 |
|---|---|---|---|
| 通道线程 | 每通道 1 | `poll()` 阻塞拉消息 | 长轮询 / WS recv |
| 工作线程 | 2 | 执行 Pipeline | HTTP 调用 |
| 定时线程 | 1 | 预算清扫、去重 GC、指标刷新 | `sleep` |
| 主线程 | 1 | 信号处理、生命周期 | 等待退出 |

**为什么不用单线程事件循环**：HTTP 客户端若要异步需引入 Asio + SSL，
复杂度陡增；而阻塞 IO + 少量线程在这个规模下更简单可靠。
2C1G 上 5 个线程的调度开销可忽略。

### 5.2 会话串行化

**同一会话必须串行处理**，否则两个工作线程同时处理同群两条消息，
回复顺序会乱，记忆写入也会竞争。

方案：按 `conversation_id` 哈希到 64 个互斥锁（条带锁）：

```
shard = hash(conversation_id) % 64
lock(shards[shard])
   ... 处理 ...
unlock(shards[shard])
```

**不用**每会话一个队列：会话数不可控，队列对象会泄漏内存。
64 个条带锁是固定开销，碰撞概率在这个规模下可接受。

### 5.3 背压

工作队列有界（容量 128）。满载时：

1. 优先保证**私聊**（更可能是真人对话）
2. 群聊消息直接丢弃并记 metric

**绝不能无界排队**：1G 机器上积压 = OOM。

## 6. 成本控制（核心设计点）

DeepSeek 定价：缓存命中输入 **0.02 元/百万**，未命中 **1 元/百万**。
**差 50 倍。** 这不是优化项，是架构约束。

### 6.1 前缀缓存为什么能命中

DeepSeek 按 token 前缀匹配缓存。一次请求的结构：

```
[ system prompt ][ 历史消息 ][ 本轮用户消息 ]
     ↑ 永远不变      ↑ 大部分不变    ↑ 每次都变
      命中           命中            必然未命中
```

只要 **system 恒定** 且 **历史是追加式**（不重写、不重排），
除最后一轮新增的 token 外全部命中。

### 6.2 三条纪律

| 纪律 | 违反后果 |
|---|---|
| system prompt 逐字节恒定 | 每轮全量未命中，成本 ×50 |
| 动态内容只放**最后一条 user 消息** | 同上 |
| 历史只追加，不改写、不重排 | 前缀断裂，从断点起全部未命中 |

**实现约束**：
- `IPersona::stable_prefix()` 返回 `const std::string`，构造后不可变
- 时间戳、召回记忆、情绪状态等**一律进尾部**，永不进 system
- 单测断言：两次调用 `stable_prefix()` 结果逐字节相等

### 6.3 可观测性

每次请求记录：

```
prompt_tokens / cached_tokens / output_tokens / 估算成本
```

滚动统计**缓存命中率**。低于 70% 时告警——说明有动态内容混进了前缀。

## 7. 错误模型

### 7.1 不用异常

理由：
- 1G 机器上崩溃重启代价高，错误必须可归类、可降级
- 异常穿透模块边界会让降级策略失效
- 成本相关错误（429、余额不足）需要专门处理分支

统一 `Result<T>`，携带 `ErrorCode` 与 `detail`。

### 7.2 错误分级

| 级别 | ErrorCode | 处理 |
|---|---|---|
| 可重试 | `kTimeout`、`kRateLimited`、`kUpstreamUnavailable` | 退避重试（最多 2 次） |
| 不可重试 | `kBadRequest`、`kUnauthorized` | 记日志，降级 |
| 业务限制 | `kBudgetExhausted`、`kUnsupported` | 静默，记 metric |
| 内部错误 | `kInternal` | 降级为固定文案 |

### 7.3 熔断

上游连续失败 ≥ 5 次 → 熔断 30 s。熔断期间直接走降级，不发请求。
避免上游故障时把工作线程全部拖死。

## 8. 可观测性

### 8.1 指标（进程内聚合，定期打日志）

| 指标 | 用途 |
|---|---|
| `msg_in_total{channel,result}` | 消息处理结果分布 |
| `reply_total{channel}` | 实际回复数 |
| `silent_total{reason}` | 静默原因分布（未 @、过期、重复…） |
| `llm_tokens{prompt,cached,output}` | 成本 |
| `llm_cache_hit_ratio` | **前缀缓存健康度** |
| `latency_ms{stage}` | 各阶段耗时 |
| `error_total{code,module}` | 错误分布 |
| `degrade_total{stage}` | 降级次数 |
| `rss_bytes` | 内存占用 |

### 8.2 日志

结构化单行 JSON，便于 grep 与后续接入采集。

必须带：`ts`、`level`、`module`、`conversation_id`、`event`。
**绝不打完整消息正文**（隐私），只打长度与哈希。

## 9. 配置与密钥

| 类型 | 载体 | 例子 |
|---|---|---|
| 密钥 | **环境变量 / `.env`** | `DEEPSEEK_API_KEY` |
| 行为配置 | `config.toml` | 温度、窗口、上限 |
| 人格 | `persona/persona.md` | 人格正文 |
| 约束 | `persona/rules.md` | 被动红线 |

纪律：
- 密钥**永不进代码、永不进仓库**，`.gitignore` 覆盖
- 配置加载失败**必须显式报错退出**，不允许静默用默认值
- 人格文件缺失 = 启动失败（空人格比不启动更危险）

## 10. 部署形态

```
/opt/super-feiyu/
├── super-feiyu            # 静态二进制
├── config.toml
├── persona/
│   ├── persona.md
│   └── rules.md
└── data/
    ├── memory.db          # SQLite (WAL)
    └── media/             # 图片/音频临时文件
```

- systemd 管理，`Restart=always`
- 内存限制：`MemoryMax=512M`（远高于目标，只为兜底）
- 无 Docker、无 Python、无 Xvfb
